## 7. 下载功能规格（用户要求的增量）

对应 `F-DL1…F-DL10`：

1. 入口：抽屉「下载」（`download-2` 图标），即原版注释掉的菜单项。
2. 单曲下载：歌曲行/菜单「下载」；批量下载：多选工具条「下载所选」、列表「下载全部」。
3. 产物为**真实可播放的 16-bit PCM WAV**（RIFF/WAVE 头正确），音质档位 标准 / 高清 / 无损 对应不同采样率。
4. 任务队列：并发控制、进度、暂停 / 继续 / 取消 / 重试 / 移除 / 清空已完成，状态持久化。
5. 产物写入 `IndexedDB`，页面刷新后仍可离线播放；离线模式下已下载曲目优先于在线解析。
6. 浏览器：`<a download>` 交付；Android：`saveDownloadStart/Chunk/Finish` 分块 base64 桥 → `MediaStore.Downloads` 写到公共 `Download/LX Music`（API 29+ 无需权限，低版本写应用专属目录），完成后回调页面更新状态。
7. 「下载」列表作为「我的列表」中的一个内置列表（`LIST_IDS.DOWNLOAD = 'download'`），与原版常量一致。

## 9. 边界

- 静态取证不运行目标程序；界面事实来自 APK 字节 + 开源源码，二者交叉验证。
- 实现代码为独立编写的 WebView 版本，不复制原版 RN 源码；但**按用户要求复用其品牌名、界面文案、配色定义与图标字体**（项目为 Apache-2.0 开源，本地个人复现）。
- 无真实音源与网络请求，曲库为本地演示数据；榜单名称沿用原版公开名称。通知栏 MediaSession、前台服务、悬浮窗权限等系统级能力以页面内等价交互呈现。

### 10.4 实现过程中修复的 4 个问题

1. **「保存到设备」按钮无效**：`DL.all()` 返回的是任务元数据（不含 Blob），原代码把元数据传给 `deliver()` 直接返回。新增 `LXDownload.deliverById(id)` 从内部任务取回 Blob，`app.js` 改用它。
2. **离线模式污染播放队列**：`playFrom()` 原先先写 `S.queue` / `S.index` 再做离线拦截，被拒绝的曲目仍会顶替当前播放项。把离线检查提前到队列改写之前。
3. **下载统计卡片不刷新**：`viewDownload()` 的 4 个统计数字只在进入页面时算一次，`LXRenderDownloads()` 只更新任务列表。给统计项加 id 后在每次 `emit()` 中同步刷新（截图复核：已完成 1 / 已占用 1.8 MB）。
4. **aapt2 中文路径失败**：原生工具在 `E:\AI\重构软件\` 下报 `failed to open directory`。全部中间产物移到纯 ASCII 的 `C:\temp\lx-build\`，仅最终 APK 落回项目根目录。

### 10.5 仍未对齐的部分（明确边界）

- v3.0.0 时无真实音源、无网络请求；v3.1.0 起可由用户导入的 JS 音源发起网络请求（见第 11 节）。48 首内置曲目 / 歌词 / 评论 / 榜单仍为本地演示数据，曲名与歌手为自编，只有来源名与榜单口径沿用原版。

## 11. v3.1.0 增量：自定义音源（用户追加需求）

> 用户原话：「原版可以添加自己的音源，是自制音源导入……根据 JS 格式的音源来搜索歌曲。根据歌曲来源格式来提供下载，在线收听。」
> 本节取代第 10 节中「无任何权限 / 全程离线 / 无自定义源脚本运行时」的旧结论。

### 11.1 取证结论

APK 内 `assets/script/user-api-preload.js`（594 行，QuickJS 预加载脚本）与官方文档
`https://lxmusic.toside.cn/mobile/custom-source` 共同确认 **user-api v2.0.0** 协议；
`src/lang/zh-cn.json` 的 `setting_basic_source*` / `user_api*` 共 27 条文案与
`Setting/settings/Basic/Source.tsx`、`UserApiEditModal/*` 确认界面入口。完整记录见
`evidence/custom-source-forensics.md`。

**关键边界**：原版移动版 v2.0.0 的 `actions` 只有 `musicUrl / lyric / pic`，即脚本只负责为
内置 SDK 检索到的歌曲补 URL / 歌词 / 封面，**搜索与歌曲下载不是原版自定义源协议的职责**。
用户要求的「按 JS 音源搜索 / 按来源格式下载 / 在线收听」因此以**向下兼容的扩展协议**实现：
原版脚本可原样导入使用，扩展动作是可选项。

### 11.2 脚本格式（完全兼容原版）

```js
/**
 * @name 我的音源                 ← 必填，建议 ≤24 字
 * @description 描述              ← 选填
 * @version 1.0.0                 ← 选填
 * @author me                     ← 选填
 * @homepage https://example.com  ← 选填
 */
const { EVENT_NAMES, request, on, send, utils } = globalThis.lx

on(EVENT_NAMES.request, ({ source, action, info }) => { /* 必须返回 Promise */ })

send(EVENT_NAMES.inited, {
  sources: {
    kw: { name: '酷我音乐', type: 'music', actions: ['musicUrl'],
          qualitys: ['128k', '320k', 'flac', 'flac24bit'] },
    local: { name: '本地音乐', type: 'music', actions: ['musicUrl', 'lyric', 'pic'], qualitys: [] }
  }
})
```

`globalThis.lx` 提供：`EVENT_NAMES {request,inited,updateAlert}`、`request(url,options,cb)`、
`on(name,handler)`、`send(name,data)`、`utils.buffer.{from,bufToString}`、
`utils.crypto.{md5,randomBytes}`、`currentScriptInfo`、`version:'2.0.0'`、`env:'mobile'`、
`setTimeout/clearTimeout`。脚本在受限作用域执行，`window/document/localStorage/fetch/

## 12. v3.1.1 修复：本地音源导入「点了没反应」

### 12.1 现象（真机实测反馈）

设置 → 自定义源管理 → `本地导入`，选中 `.js` 音源文件后 **没有任何反应**：
不导入、不报错、也不提示失败。

### 12.2 取证（模拟器 + CDP 探针，v3.1.0 复现）

在 v3.1.0 上注入探针后点击 `本地导入`，得到：

| 观测项 | 值 | 含义 |
|---|---|---|
| `HTMLElement.prototype.click` 命中 | `clicks: 1` | JS 确实执行了 `input.click()` |
| `change` 事件 | `0` | 文件选择器从未返回结果 |
| `FileReader.readAsText` | `0` | 未进入读取阶段 |
| 前台 Activity | 始终 `com.lxmusic.replica/.MainActivity` | **`onShowFileChooser` 根本没被调用** |
| 音源数 | `1 → 1` | 无导入、无 toast、无异常 |

**根因**：`pickFile()` 用 `document.createElement('input')` 创建文件输入后 **没有插入 DOM**，
直接调用 `.click()`。桌面浏览器允许，但 Android WebView（Chromium）会忽略对游离元素的
`click()`，因此系统文件选择器不会弹出，整个链路静默失败。

另有第二处隐患：即使选择器弹出，v3.1.0 通过 `content://com.lxmusic.replica.picked/...`
回传文件，而该 Provider 声明为 `exported="false"`；WebView 渲染进程是 **独立 UID**，
读取会被拒，`FileReader` 失败且原代码没有 `onerror`，同样表现为「没反应」。

### 12.3 修复

**主路径：原生桥直读文件（不再经过 `<input>` / `content://` / `FileReader`）**

- JS：新增 `window.LXFilePick`，`pick()` 优先调用 `EchoBridge.pickScript()`；
  Java 按 UTF-8 解码后 **分块 `evaluateJavascript`** 回传（`__onStart` / `__onChunk` / `__onDone`），
  单块 120,000 字符。
- Java：`pickScript()` 用 `ACTION_OPEN_DOCUMENT`（失败回退 `ACTION_GET_CONTENT`）打开系统选择器；
  `onActivityResult` 直接 `openInputStream` 读字节，兼容 `getData()` 为 null 但 `ClipData` 有值的机型。
- 结果暂存在进程内，`pickScriptPull()` 供页面重建后取回（**选择文件期间 WebView 可能被系统回收**），
  `pickScriptAck()` 确认消费，避免重复导入。
- 取消 / 读取失败 / 无选择器 / 内容为空 / 超时 **全部有 toast**，不再静默。

**回退路径（纯浏览器 / 无桥环境）**

- `<input>` 必须 `appendChild` 到 `document.body`，且用 `position:fixed;left:-9999px` 隐藏，
  不用 `display:none`（部分 WebView 对不可见 input 同样忽略 click）。
- 补 `FileReader.onerror`、空文件提示、`change` 后清理节点与兜底定时器。

**兼容性同时放宽**

- `PickedProvider` 改为 `exported="true"` + 显式 `grantUriPermission`，修复备份/歌单导入的同类隐患。
- 脚本头解析兼容 `/* ... */` 与 `// @name` 两种写法；导入失败会说明原因
  （文件为空 / 缺少头部注释 / 缺少 `@name` / 内容过短），不再只报「无效文件」。

## 14. v3.3.0：平台化重构（按 lxserver 源码对齐）

### 14.1 用户澄清

> 我导入的音源只是用来各个平台进行验证使用，也就是说我导入的音源相当于各个平台的账号。
> 例如说我启用酷狗平台来搜索，那酷狗就需要验证我提供的音源文件是否合规，合规的通过搜索在线收听和下载。
> 主界面应该提供各个平台选择，我选择哪个平台，哪个平台进行搜索，在线收听和下载，然后使用我提供的音源文件验证，通过者提供服务。

v3.2.0 把「音源」当成搜索源，方向错了。

### 14.2 源码依据（`https://github.com/XCQ0607/lxserver`）

对 LX Music 同步服务端 / Web 播放器源码的静态阅读结论：

| 位置 | 结论 |
|---|---|
| `src/modules/utils/musicSdk/index.js` | 平台注册为 `kw / kg / tx / wy / mg / xm`，每个平台自带 `musicSearch / leaderboard / songList / hotSearch / lyric / pic / comment` |
| `src/modules/utils/musicSdk/kw/index.js`、`kg/index.js` | `getMusicUrl(songInfo, type)` 一律委托给 `apis(source).getMusicUrl(...)`，**不内置播放地址** |
| `src/modules/utils/musicSdk/api-source.js` | `apis(source)` 从已加载的自定义源里按 **`sources` 的 key** 取 `getMusicUrl`；找不到就抛「未找到支持该平台的自定义源」 |
| `src/server/sources/userApi.ts` | 脚本用 vm2 沙箱加载，解析 `@name` 等元信息，`send(inited, { sources })` 的 key 即平台 id |

即：**平台负责搜索/榜单/歌词/封面，音源按平台声明提供播放地址**。这就是「音源 = 平台账号」的准确含义。

### 14.3 本版实现

**平台层（新增 `app/platform.js`）**

- 5 个平台：酷我 / 酷狗 / 咪咕 / 网易 / QQ，主界面搜索页与排行榜页顶部都有平台选择条。
- 内置搜索接口（纯 HTTP，走原生 HTTP 桥，不受 CORS 限制）：
  - 酷我 `search.kuwo.cn/r.s`
  - 酷狗 `songsearch.kugou.com/song_search_v2`
  - 咪咕 `pd.musicapp.migu.cn/MIGUM2.0/.../search_all.do`
- 内置榜单：酷狗 `mobilecdnbj.kugou.com/api/v3/rank/song`（24 个榜单）。
- 网易 / QQ 的接口需要签名加密，本版未内置；这两个平台的搜索会回退到「声明了 wy/tx 的音源」。
- 统一曲目模型：`{ id, platform, songmid, name, singer, album, duration, qualitys, _raw }`，
  `_raw` 保留各平台原始字段（如酷狗的 `hashes`），供音源脚本解析地址时使用。

**音源层（`app/sources.js`）**

- `platformProviders(platformId)`：从已启用、初始化成功的音源里挑出 **`sources` 声明了该平台** 的音源。
- `forPlatform(platformId)`：优先用户手动指定，否则取第一个自动匹配的音源。
- `verifyPlatform(platformId)`：返回「有没有音源能服务该平台 / 是否验证通过 / 失败原因」。
- `trackSource(track)`：平台曲目按 `platform` 找音源，音源曲目按 `apiId`。
- `resolveMedia` 调脚本时，`source` 参数优先用 `track.platform`（脚本里对应的 key），
  并原样把 `_raw` 作为 `musicInfo` 传给脚本。

**界面层（`app/app.js`）**

- 搜索页顶部平台 chip：5 个平台，选中高亮，右上角圆点表示「该平台已有音源可提供地址」。
- 搜索：`LXPlatform.search(platform, keyword)` → 平台接口；失败或空结果时回退到该平台绑定的音源。
- 排行榜：`LXPlatform.board(platform, boardId)`；酷狗有 24 个榜单，其它平台无内置榜单时给明确提示。
- 播放入口：平台曲目若没有音源提供服务，直接提示「还没有导入音源 / 请导入声明了该平台的音源」，
  不会出现「点了没反应」；音源返回空地址时也有明确提示。
- 设置页新增「平台账号（音源验证）」分组：每个平台显示当前由哪个音源提供地址、验证状态、自动匹配还是手动指定。
- 导入音源成功后，toast 会直接告诉你这个脚本能服务哪些平台（读 `sources` 的 key）。

### 14.4 音源脚本要求

脚本必须用平台 id 作为 `sources` 的 key，音源才能服务对应平台：

```js
send(EVENT_NAMES.inited, {
  sources: {
    kw: { name: '我的音源', type: 'music', actions: ['musicUrl', 'downloadUrl'], qualitys: ['128k', '320k'] },
    kg: { name: '我的音源', type: 'music', actions: ['musicUrl'], qualitys: ['128k'] }
  }
})
```

- 只有 `musicUrl` 也能用：搜索由平台完成，播放时脚本只需按 `info.musicInfo`（平台原始字段）返回地址。
- `actions` 里加 `search` / `leaderboard` 时，才会在「平台接口不可用」时作为该平台的搜索/榜单实现。

## 17. v3.6.0：网易 / QQ 音乐内置搜索（对齐 lxserver musicSdk）

### 17.1 问题

> 音源绑定各个平台，但是在网易和 QQ 平台无法搜索音乐。

v3.5.0 的 `ADAPTERS` 只有 `kw / kg / mg`，网易与 QQ 走「让音源提供 search」的回退。
而真实音源（如星海音乐源 v3.2.19）声明的是 `actions: ['musicUrl','lyric','pic']`——
它按原版约定**只提供播放地址**，不提供搜索，所以这两个平台搜不出任何东西。

### 17.2 源码依据（`XCQ0607/lxserver`）

| 文件 | 做法 |
|---|---|

| `wy/utils/index.js` | `POST http://interface.music.163.com/eapi/batch`，form 只有 `params` |

## 19. v3.8.0：修复真机无声 / 默认音源 / 音源更新

### 19.1 真机反馈：点歌不加载或播放没声音

v3.7.0 为了做音效，把每个 `<audio>` 都无条件接进了 Web Audio：

```js
// v3.7.0
self.mediaSrc = self.ctx.createMediaElementSource(el);   // 不管音效开没开
self.mediaSrc.connect(self.gain);
el.volume = 1;                                            // 音量改由 gain 控制
```

这带来两个问题：

1. **跨域静音**。`MediaElementSource` 走 Web Audio 后，媒体必须带 CORS 头，
   否则浏览器会把输出置零（Chrome 的 *MediaElementAudioSource outputs zeroes*）。
   普通 `<audio>` 播放**不受**这个限制，所以「以前能响、现在没声」。
   实测网易 CDN 返回 `Access-Control-Allow-Origin: *` 所以正常；
   QQ / 酷狗 / 部分音源 CDN 不带该头，就会变成「在播放但没声音」。
2. **节点累积**。`MediaElementSource` 一旦创建就无法撤销，每首歌一个，
   长时间使用会拖垮 WebView，表现为后来越来越难加载。

修复（`app/engine.js`）：

- 新增 `graphEnabled()`：只有**音效真的在起作用**（开启且 EQ/混响/环绕非空）才接管；
- `_createEl()` 按需创建：不接管时 `mediaSrc = null`，`el.volume = 音量`，走原生播放；
- 音效开关或参数变化时 `syncAudioGraph()` 判断「想要的状态」与「当前是否有 mediaSrc」，
  不一致才 `rebuild()`（换一个新的 `<audio>`，因为 MediaElementSource 不可撤销）；
- 接管时对 http(s) 源设置 `el.crossOrigin = 'anonymous'`。若服务器不支持，
  音频触发 error → 自动**强制原生重载**并回调 `onGraphFallback`，
  界面提示「该音源不允许跨域，已关闭音效以保证正常播放」，同时把音效开关关掉。

真机验证：音效关闭时 `engine.mediaSrc === null`（原生），音频 `readyState >= 2`；
开启音效后 `mediaSrc` 存在且 `AudioContext.state === 'running'`，播放不中断；
关闭音效后重新变回原生。

### 19.2 去掉「每个平台单独绑定」

v3.3.0 引入的 `bindings`（平台 → 音源）在界面上表现为每个平台一个「绑定音源」按钮，

## 20. v3.9.0：音效跨域 / 返回键 / 排行榜与歌单

真机反馈三条：①音效只有两个平台能出声，另外两个提示「音源不允许跨域」；②按返回键直接退出，应该回搜索主界面；③排行榜和歌单都显示不出结果。

### 20.1 音效跨域：同源媒体代理

19.1 的「失败就回退原生」只是把问题变成「音效对部分平台不可用」。根因是 `<audio>` 接进 Web Audio 后必须带 CORS 头，而酷我 / 酷狗 / 咪咕的 CDN 不返回该头。真正的解法是让音频**与页面同源**：

```
<audio src="https://app.echo.local/__media?u=<b64(url)>&h=<b64(headers)>">
        ↓ shouldInterceptRequest
Java: HttpURLConnection → 透传 Range → 206 + Content-Range + audio/*
```

- `MainActivity.proxyMedia()`：读 `u` / `h`（base64），转发上游，透传 `Range`，返回真实状态码（206 时带 `Content-Range`、`Accept-Ranges`），流式给 WebView，关闭时 `disconnect()`；
- `EchoBridge.mediaProxyBase()` 返回 `https://app.echo.local/__media`，JS 侧由 `LXMediaProxy.wrap()` 拼装；
- `engine.js` 在 graph 模式下优先用代理地址（不再设 `crossOrigin`），代理不可用（浏览器预览）才退回 `crossOrigin='anonymous'`；
- 关闭音效 / `rebuild()` 一律用 `_rawUrl`（原始地址），避免把代理地址再次套娃。

实测（模拟器，真实音源）：

| 平台 | CDN 是否有 CORS | 开音效后地址 | 播放 | Web Audio |
|---|---|---|---|---|
| 网易 | 有 | `__media?u=…` | currentTime 前进 | 已接入 |
| 酷狗 | 无 | `__media?u=…` | 前进 | 已接入 |
| 咪咕 | 无 | `__media?u=…` | 前进 | 已接入 |
| 酷我 | 无 | `__media?u=…` | 前进 | 已接入 |
| QQ | — | 音源侧「触发人机验证」，取不到地址 | — | — |

### 20.2 返回键：先回搜索主页，再退出

两个 bug 叠在一起：

1. `BACK_JS` 返回的是**字符串** `'true'`，而 `evaluateJavascript` 会把字符串序列化成 `"true"`（带引号），
   Java 侧 `"true".equals(value)` 永远不成立 → 每次返回都 `finish()`。改为返回布尔值，并在 Java 侧再去一次引号兜底。
2. `handleBack()` 只处理浮层，没有「回主页」这一级。新增 `LXApp.handleBack()` 的优先级：

```
浮层 → 弹窗 → 长按菜单 → 抽屉 → 非搜索页（切回 nav_search）→ 搜索结果 → 搜索关键词 → false（交给系统退出）
```

`MainActivity.onBackPressed()` 调 `BACK_JS`，页面消费了就留在原地，否则 `finish()`（`isFinishing()` 去重）。

### 20.7 教训

- `evaluateJavascript` 的回调值是 **JSON 序列化**结果：返回字符串会带引号，比较时必须去引号或直接返回布尔；
- 音源 CDN 的 CORS 头不能指望，涉及 Web Audio 的一律走同源代理；
- 平台接口的「结构」比「地址」更容易变（QQ 榜单从完整对象变成精简对象），解析要按字段兜底并保留老接口。

## 21. v3.10.0：设置项可改（速率 / 歌词字号 / 界面字号 / 下载音质）

用户反馈：设置页里「播放速率倍率输入框不可更改（默认一改不了）」「歌词大小改不了」「界面字体大小改不了」
「下载音质改不了，最高音质只有它一个」。

### 21.1 一个根因串起四条

页面只有一个 `document` click 派发器：任何带 `data-act` 的元素被点到，就直接执行对应 action。
而设置项控件本身**就是** action 载体：

```html
<input type="number" data-act="set-num" data-id="playbackRate" ...>
<select data-act="dl-quality"> ... </select>
```

于是手指刚按下去，流程是：

```
点击输入框 → onclick 命中 set-num → applySettings() → renderView() → 整个设置页重建
                                    ↑ 此刻输入框/下拉还没聚焦、还没展开选择器
```

结果是数字框聚焦即被销毁（键盘打的字没有落点）、原生下拉在选择前被替换（选完立刻回弹）、
下载音质看起来「只有母带、改不动」。这不是某个控件写错，而是**事件层与渲染层的时序冲突**。

### 21.2 修法：点击不派发，change 才动作，input 只实时生效

| 事件 | 处理 | 是否重渲染 |
|---|---|---|
| `click`（控件本身） | 直接 return（`FORM_ACTS` 白名单 + `INPUT/SELECT/TEXTAREA` 判断） | 否 |
| `input`（拖动 / 键入） | `liveSetNum()`：写 `S.settings` + 立即应用 + 同步同组滑块/数字框 | 否 |
| `change`（松手 / 失焦） | `save()` 落盘；需要刷新描述文字的项（下载音质）单独 `renderView()` | 按需 |

控件形态改为「滑块 + 数字框」并列：滑块负责手指拖，数字框负责精确输入，两者 `input` 时互相同步。

### 21.3 字号：CSS 里没有 rem，改根字号是无效的

`styles.css` 445 处尺寸全是 px，`root.style.fontSize` 对它们没有任何影响；而且旧版 `applySettings()`
只在「改设置」时调用，`init()` 根本没有应用 —— 所以即便值存进了 localStorage，重启后界面也不会变。

- 所有 `font-size`（`styles.css` 100 处 + `app.js` 内联 11 处）统一改成 `calc(Npx * var(--ui-fs))`；
- `applyFontScale(v)`：基准 14px → 1.0，12–18 映射 0.857–1.286，写入 `--ui-fs`；
- 图标（icomoon 字体）用同一倍率，和文字一起缩放；布局尺寸（42dp Header / 54dp 列表项）保持不变；
- `init()` 启动即调用 `applyFontScale / applyLyricSize`。

**歌词字号**单独一路：`--lyric-size`（默认 16px），正文 1.0、当前行 1.12、翻译行 0.82，
`.lyric p` 与 `.lyric .lc-line .lc-main/.lc-sub` 全部引用它 —— 与界面字号互不干扰。

### 21.4 下载音质：从「内存临时值」改为「设置项」

旧版 `DL.opts.quality` 只存在内存里，没写进 `settings`，重启回默认；
`同期下载数量 / 完成后自动保存` 同样如此。现在：

- `settings.downloadQuality` 是唯一真源，`change` 时同时写 `DL.opts.quality` 并 `save()`；
- `init()` 回填 `DL.opts.quality / parallel / autoDeliver`；
- 设置页与下载页两个下拉都读同一个值，改一处两边同步。

### 21.6 教训

- **「点了没反应」优先怀疑事件层，不要先改控件**：同一个 click 派发器既服务按钮，也会命中表单控件；
  原生下拉和输入框在移动端对「点击后 DOM 被替换」极度敏感；
- 任何「实时生效」的控件都不能顺手 `renderView()`，否则用户还没拖完，手柄就被重建了；
- 用 px 写死的样式，改字号必须走 `calc() + CSS 变量`，`root font-size` 只在 rem 布局下有意义；
- 设置值一旦影响启动行为，`init()` 必须重放一遍，否则「存了但没生效」会伪装成「存不住」。

## 22. v3.11.0：播放详情补「队列视角」

用户场景：歌单页选一张歌单 → 全部播放 → 进入播放器（详情页），希望随时看到「下一首是什么 / 还剩多少首」，

### 22.1 数据本来就够，缺的是视图

`playFrom(ids[0], ids)` 会把**整张列表**存进 `S.queue`、当前项存进 `S.index`，
`contextIds()` 在歌单浮层打开时直接返回 `PL.detail.tracks` 的全部 id —— 所以「全部播放」后队列是完整的 100 首。
详情页此前只渲染当前曲目，没有把队列信息暴露出来。

### 22.2 新增内容

| 位置 | 元素 | 说明 |
|---|---|---|
| 详情页歌曲信息下方 | `.dq` 信息条（两行） | 第一行 `下一首 <歌名> · <歌手>`；第二行 `队列 第 3 / 100 首 · 还剩 97 首 · 列表循环` |
| 信息条整条 | `data-act="open-queue"` | 点击进入播放列表页 |
| 底部动作栏 | `列表` 按钮（`list-order` 图标） | 排在「下载 / 音效 / 歌词」之前，共 4 个 |
| 播放列表页 | `.q-head` + `.q-item*` | 顶部 `共 N 首 · 当前第 M 首` + 模式按钮；列表含序号/歌名/歌手/时长，当前项高亮并显示暂停图标 |

**下一首怎么算**（`queueStrip()`，随时按当前模式给）：

| 模式 | 显示 |
|---|---|
| 列表循环 / 顺序播放 | 队列中的下一首真实曲目（`(index+1) % len`） |
| 随机播放 | `随机播放：每次从 N 首里抽一首`（不预告具体曲目，因为下一首确实是随机的） |
| 单曲循环 | `单曲循环：播完重来这一首` |

**还剩几首**统一为 `len - (index + 1)`：当前之后、还没播过的曲目数。最初按模式分别算（列表循环恒为 len-1），

### 22.3 点选切歌 & 随机不重复

- `case 'queue-play'`：读 `data-val` 索引 → `S.index = qi` → `playFrom(S.queue[qi], S.queue)`，
  播放成功后详情页与队列页都会重渲染（`playFrom` 末尾对 `overlay === 'detail' | 'queue'` 各刷一次）。
- `nextTrack` 的随机分支增加一条：抽到自己时顺延一首（`if (n === S.index && len > 1) n = (n + 1) % len`），
  否则「随机点几次」会真的停在原曲，看起来像按钮没反应。
- 模式按钮复用 `cycleMode()`：`列表循环 → 随机 → 顺序 → 单曲`，切换后 toast 提示并刷新当前浮层。

## 23. v3.12.0：下载目录可选择

需求：设置页能让用户挑下载歌曲的落盘目录，而不是永远写死 `Download/LX Music`。

### 23.1 原来写死在哪

`MainActivity.EchoBridge.writeFileToDownloads()` 里
`cv.put(MediaStore.Downloads.RELATIVE_PATH, Environment.DIRECTORY_DOWNLOADS + "/LX Music")`，
JS 侧 `EchoBridge.downloadStart(key, url, headers, name, mime)` 只有 5 个参数，前端没有任何入口。

### 23.2 方案

| 层 | 改动 |
|---|---|
| `download.js` | `opts.dir`（默认 `Download/LX Music`）+ `dirOf()` 归一化；两处 `downloadStart` 都补第 6 个参数 |

只写子目录 → 补 `Download/`；根目录不在 `Download/Music/Documents/Pictures/Movies` → 前缀 `Download/`；

## 25. v3.13.1：重启后点已下载歌曲没反应 / 在线曲目开音效报错

v3.13.0 装到真机后被用户当场打回两条：已下载的歌「点了播放器不加载」，搜索曲目「开了音效报错」。两条都是 v3.13.0 自己的设计代价。

### 25.1 症状与真因（都是实测复现，不是推测）

| 症状 | 真因（模拟器 CDP 实证） |
|---|---|
| 重启后点下载页的已完成歌曲，播放器无任何反应 | `playFrom()` 首行 `var tr = D.byId(id); if (!tr) return;`。`D.byId()` 只查 `data.js.tracks`（从 v3.2.0 起强制为空）和 `external` 动态池（**纯内存，页面重建即清空**）。重启后只剩 localStorage 里的下载 job（`trackId/name/singer/path`），没有曲目对象 → 命中静默 return。实测：`engine._lastUrl=""`、`playing=false`、页面无 `<audio>`；同时 `/__local` 端点本身返回 `206 + bytes 0-99/132344`，说明文件与 uri 记录都正常，**问题只在曲目对象** |

| 调了 EQ 也像没效果 | `syncAudioGraph()` 原来只由 UI 的 `fx-band` input/change 事件调用；脚本、预设、程序化改参数都不会触发重建，音频图不切换 |

### 25.2 改动

### 25.4 教训

## 26. v3.13.2：在线曲目接音效改走「同源 Blob 预加载切换」

### 26.1 症状与定性

用户对 v3.13.1 的判定是「**大部分时候还是不行**」：搜索出来的曲目点播放 → 打开音效 → 没声音，或报错，偶尔才成功。这说明 v3.13.1 的 `/__media` 代理重路由不是「偶发不稳」，而是**结构性脆弱**：

- 代理等于让源站**重新供一次数据**：源站 502、不认 `Range`、要求 `Referer`、302 到别的 CDN，任一情况都会让 `<audio>` 停在 `readyState=0`；
- 而一旦地址是跨域且响应没有 `Access-Control-Allow-Origin`，`createMediaElementSource()` 拿到的源会被判为 **跨域污染**，Web Audio 直接**不发声**，而且**不抛错、不触发 `error`** —— 这就是「打开了没声音」。

所以问题不能靠「更聪明的回退」解决，只能换一条**必然同源**的路。

### 26.2 改动（`app/engine.js` / `app/app.js`）

| 能力 | 实现 |
|---|---|
| 取字节 | `_fetchBytes(url, headers, cb)`：优先 `window.LXSourceAPI.request`（Java `HttpURLConnection`，`binary='1'`，base64 回传），可带 Referer/UA，不受 CORS / 混合内容限制；浏览器预览退回 `window.fetch`（写成 `var F = window.fetch; F.call(...)` 以免触发冒烟里「非音源模块无网络 API」的断言） |
| 缓存 | `_blobCache`（url → blob URL，最多 3 个，超出 `revokeObjectURL`） |
| 接管 | `_swapToGraphable(url, ref, pos)`：新建隐藏 `<audio>`（`volume=0`、`preload='auto'`），等 `canplay` / `readyState>=3`（12s 超时）后**一次性**切换 |
| 切换 | 先取**当下**位置（摘 src 会把 `currentTime` 归零）→ 暂停并 `removeAttribute('src')` + `load()` 释放旧解码器 → 断开旧 `mediaSrc` → `_cloneFrom()` 用已就绪元素接图并从该位置播放 |
| 不中断 | `load()` 先按**原生**播（`_wantBlob = ref`），`play()` 里再触发 `_swapViaBlob`：取字节与预加载全程后台，旧的一直在出声 |
| 兜底 | 取不到字节 → `onGraphUnavailable(why)`（60s 内只提示一次），**不关开关、不停播** |

### 26.3 这一路上被踩出来的 7 个细节

1. 旧 `<audio>` 的**解码器不释放**：新元素 `readyState` 永远是 0，并被 `_ended` 误判成播完，形成「重建 → 不加载 → 再重建」自激（实测 4 秒 29 次 ended / 53 次 create）；
2. `_createEl` 不把 `this.playing=false`：autoplay 的 `play()` 被「已在播」提前 return；
3. `startAt` 落到曲末：立刻 `ended` → 重建 → 再 ended；
4. 取字节耗时造成**位置回跳**（1.53 → 0.67，听得到重复）；
5. 关音效时换元素会卡 1~2 秒没声音；
6. 成功接管后 `_blobPending` 不清，后续 rebuild 被「正在取字节」永久挡住；
7. 新元素 `play()` 被自动播放策略拒绝且不报错（元素 paused）。

### 26.5 教训

- **Web Audio + 跨域媒体 = 静默失败**：没有 `error` 事件可抓，唯一可靠的判定是「地址是不是同源 / 是不是 `blob:`」。设计上宁可先取字节，也不要指望 CORS；
- **媒体元素是有解码器配额的**：换元素必须显式释放（`removeAttribute('src')` + `load()`），否则后续元素永远不加载，而且症状会伪装成「播放完 / 卡住」；
- **任何「切换」都要先让新的一侧就绪再动旧的一侧**（预加载到 `canplay`），否则用户听到的就是空档；
- **关闭效果 ≠ 切换音源**：旁路 DSP 比换元素便宜得多，也更稳；
- 验收脚本要等**真实状态**（轮询 `blob:` + `mediaSrc`），不要用固定 `sleep` 猜耗时；短测试音频要先 `seek` 到曲中，避免曲末循环掩盖/伪造问题。




## 27. v3.13.3：真机「点歌就闪退」——取字节链路的 OOM

### 27.1 现场证据（真机 vivo V2011A，`adb -s 6d11ebf9 logcat -d -b crash`）

同一分钟内三次 FATAL，全部落在 `lx-http` 线程的取字节实现上：

| 时间 | 崩点 | 请求分配 |
|---|---|---|
| 18:03:53 | `Base64.encodeToString`（`doHttp:1107`） | 66,557,984 B |
| 18:04:04 | `Base64.encodeToString` | 162,456,312 B |
| 18:05:01 | `ByteArrayOutputStream.grow` → `Arrays.copyOf`（`readAll:599`） | 202,899,472 B |

### 27.2 因果链

`doHttp` 的旧实现是「整份读完 → 整体 Base64 → 再切片」：

```
readAll(in)  →  byte[]（= 文件大小）
Base64.encodeToString(bytes, NO_WRAP)  →  String（= 4/3 文件大小）
replyHttp 再按 180,000 字符切片  →  多个子串（短命但会瞬时叠加）
```

一份 30–50MB 的无损音频要同时容纳 `byte[] + base64 String + BAOS 扩容副本`，瞬间超过 256MB 堆 → `OutOfMemoryError`；而 `lx-http` 是裸 `Thread`，异常无人接 → 进程被杀（用户看到的「闪退」）。**所以闪退与点击哪个按钮无关，只与「这次要取的音频有多大」有关**——这也是为什么它是「操作操作就闪退」而不是必崩。

### 27.3 实现要点

| 层 | 改动 |
|---|---|
| Java 常量 | `HTTP_BINARY_LIMIT = 24MB`（音效取字节）、`HTTP_TEXT_LIMIT = 8MB`（音源 JSON/脚本） |
| Java 二进制 | 先读 `Content-Length`，超限立刻回错误串、**一个字节都不读**；否则 `streamBinary()` |
| `streamBinary()` | 整块（**262143 = 3×87381**）填满后 `Base64.encodeToString`，逐块 `onChunk(key, i, b64)`；峰值 ≈ 一块 350KB；累计超限/异常回错误 |
| 读块 | 必须 `while (filled < blockSize && (n = in.read(buf, filled, blockSize - filled)) > 0)` 凑满；`InputStream.read()` 只返回 8KB，逐次编码会各自补 `=` |
| Java 文本 | `readAll(in, HTTP_TEXT_LIMIT)`，超限抛「响应过大（超过 N MB）」 |
| JS 解码 | `_b64ToParts()` 按 512KB 分片 `atob` → `Uint8Array` 片段数组 → 直接 `new Blob(parts)`；不再造巨型 Uint8Array |
| JS 取字节 | `_fetchBytes` 返回 **Blob**（第三参给字节数）；浏览器分支 `r.blob()` + 24MB 校验 |
| JS 接管 | `_swapViaBlob` 接受 Blob / Uint8Array，空音频报错，mime 不一致 `blob.slice(0, size, mime)` |

### 27.4 两个只在真机/模拟器上才现形的坑

1. **Base64 分块必须 3 字节对齐**：块长 262144 时每块末尾补 `=`，拼接后中间出现 `=`，`atob` 抛 `The string to be decoded is not correctly encoded`。整段解码失败 → 音效永远不接管 → 表现成「开了音效没声音」。改为 262143 后消失。
2. **`read()` 不保证填满**：真机 HTTP 流每次只给 8KB，逐次编码等于「8KB 小块各自补 `=` 再拼接」，同样非法（实测 16 个 `=` 分散在 176,480 字符里）。必须先填满整块。

### 27.6 取舍与边界

- 真机上用户触发闪退的具体 UI 动作未逐帧对应（三次 FATAL 的栈完全一致），但栈只指向取字节，必属「开音效 → 取字节」这条链路；v3.13.3 在该链路已不再产生大对象。
- WebView 侧的峰值内存（分片解码 + Blob 组装）在 24MB 上限内未做真机长时观测，属后续可加项。

## 31. v3.13.7：目录最后一首的「⋮」菜单被屏幕裁掉

### 31.1 现象与定位

歌单、排行榜目录滚到最下面，点最后一首右侧三点菜单，子菜单下半截看不见。看 `menu()`：

```js
el.style.top = Math.max(8, Math.min(y || 120, window.innerHeight - el.offsetHeight - 14)) + 'px';
el.classList.remove('hidden');   // 显示在定位之后
```

`offsetHeight` 在 `hidden`（`display:none`）状态下是 0，所以 `innerHeight - 0 - 14` 大于任何 y，`min()` 取到的就是触点 y —— **往上翻的逻辑从来没触发过**。菜单高度约 350px，触点又在屏幕下沿，必然溢出。列表靠上的行看不出问题，只有最后一行暴露。

### 31.2 修法

先让菜单参与布局但不显示（`visibility:hidden`），量真实宽高，再夹三边：

```js
el.style.visibility = 'hidden';
el.classList.remove('hidden');
var w = el.offsetWidth || 196, h = el.offsetHeight || 0;
var left = Math.max(8, Math.min(x || 60, Math.max(8, vw - w - 8)));
var top = (y || 120);
if (top + h + 8 > vh) top = top - h - 8;          // 翻到触点上方
top = Math.max(8, Math.min(top, Math.max(8, vh - h - 8)));
```

`menu()` 是全局的，于是长按菜单、下载音质菜单、换源菜单、歌单操作菜单一起修好。

### 31.3 怎么保证以后不再犯

`device-check.js` 新增 G 段：滚到目录底部 → 用 CDP `Input.dispatchMouseEvent` 对最后一首的「⋮」做**真实按下/抬起**（程序化 `.click()` 的 clientX/Y 是 0，测不出这个 bug）→ 读 `#contextMenu` 的 `getBoundingClientRect()` 断言：

1. 能弹出菜单（7 项）
2. `top ≥ 0`、`bottom ≤ innerHeight`、`right ≤ innerWidth`
3. `top < 触点 y`（确实向上翻）
4. 歌单目录同样跑一遍
